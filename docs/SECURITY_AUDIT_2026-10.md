# Security audit — 2026-10-23

This audit maps the October 2026 internet-facing security review to the implementation. The code and automated tests remain authoritative. The review was performed against baseline `ed2d4eedaed99207ae0e5950b79ef70d847947a3`; qualification evidence for the remediation is recorded in `BUILD_STATUS.md` after the exact-head gate completes.

## Accepted limits and deployment controls

- DNS validation cannot by itself eliminate a provider-side DNS rebinding or routing compromise between validation and transport connection. The application allowlist greatly narrows destinations, but production egress must also deny loopback, link-local, RFC1918/internal, cloud-metadata and other non-approved destinations. Verify the effective firewall from the deployment host; do not treat application checks as the whole SSRF boundary.
- Data already saved in an authenticated browser's offline cache cannot be remotely erased while that device remains offline. Caches contain only the bounded personal roster projections, are user-namespaced, and are cleared at the next observed logout/account switch.
- Physical authenticator, real VAPID/provider, reverse-proxy, firewall, restored-backup and public-host penetration checks are deployment evidence, not claims made by unit or CI qualification.
- Passkeys remain supported. Automated tests validate server ceremonies and replay/origin policy; a real or virtual authenticator ceremony remains part of staging acceptance.
- Safe fresh-auth continuation may later store a short-lived, single-use, user/session-bound server-side intent containing an allowlisted action and validated parameters. Successful re-authentication may execute only that intent. Arbitrary POST-body replay, browser-stored secrets and generic redirect-driven mutation remain prohibited.

## Controlled staging secret rotation

Staging configuration values were exposed in operator diagnostics in October 2026. Do not reproduce those values in tickets, chat, documentation, logs or Git. Immediately restrict or remove the diagnostic artifact wherever the platform permits, review its audience and access logs, prevent further environment rendering, and treat the values as compromised. Rotation itself requires a verified PostgreSQL plus `/app/data` backup, encrypted recovery custody and a separately approved maintenance window.

| Secret or state | Actual dependency and rotation effect | Safe rotation boundary |
|---|---|---|
| PostgreSQL role password | Independent of application cryptography. Existing pooled connections may continue until recycled; new connections require the new password. | Change the intended staging database role and the Portainer connection setting as one controlled operation, then restart app and scheduler and prove database/readiness/migration health. Do not publish PostgreSQL or paste the value into a command transcript. |
| `ONTRACK_SECRET_KEY` | Domain-separated Fernet keys encrypt TOTP secrets and Web Push subscription endpoint/key material. It also keys login/MFA throttle identifiers. Trusted-device, CSRF, invite, recovery-code, reset and challenge tokens are stored with ordinary SHA-256 rather than this key, so changing it does **not** itself revoke sessions. | Do not replace it in place. Either implement and qualify old-key decrypt/new-key re-encryption before cutover, or explicitly re-enrol every TOTP factor and browser Push subscription. Current code has no dual-key migration path. Old throttle buckets become unreachable and may expire normally. Retain the old key only in encrypted break-glass custody until verified recovery completes, then destroy it under an approved procedure. |
| `ONTRACK_CREDENTIAL_PEPPER` | Every PIN/password Argon2 verification appends the single configured pepper. A direct change makes every existing primary credential fail. It does not change passkey public keys, TOTP ciphertext or recovery-code hashes. | Current code has no previous-pepper fallback. Choose and qualify either a bounded dual-pepper verify-and-rehash migration or an operator-controlled reset of every account's primary credential. Prove final-Admin recovery first and do not assume passkeys alone satisfy all primary-login/grant-activation flows. |
| Trusted devices and sessions | Opaque session tokens and CSRF values are random and stored as SHA-256 hashes; neither application-secret nor pepper rotation automatically invalidates them. Credential replacement and supported account/device controls advance/revoke the relevant state. | Decide explicitly whether incident scope warrants global sign-out. If so, use a reviewed database/service operation that advances account auth epochs or revokes devices, then verify all old sessions fail. Do not claim rotation alone signed users out. |
| TOTP and recovery | TOTP ciphertext requires the old application secret. Recovery codes are one-way SHA-256 hashes and remain usable if their factor remains recoverable. | Back up first, inventory confirmed factors without exposing secrets, prove an Admin recovery path, then migrate ciphertext or schedule re-enrolment. Never cut over the key and discover factor loss afterward. |
| Passkeys | Stored credential IDs/public keys/counters are not encrypted with either deployment secret. WebAuthn continues to depend on the exact RP ID and origin. | No key migration is required, but test real passkey login after maintenance and do not change RP identity. Passkeys are recovery assistance, not a substitute for the primary-credential migration decision. |
| Web Push/VAPID | Subscription payloads are encrypted by `ONTRACK_SECRET_KEY`; VAPID public/private keys are separate environment values. Changing either application-secret encryption or the VAPID key pair can require browsers to subscribe again. | Keep Push disabled unless deliberately qualified. Re-encrypt subscriptions when only the application secret changes; when VAPID changes, publish the new public key and require fresh browser subscriptions. Never store the private key in the database backup or Git. |
| Portainer and backups | Portainer holds runtime configuration; database dumps retain hashes and encrypted blobs but not the environment keys needed to use them. Git-backed stack updates and mutable tags can change runtime configuration or image content independently of acceptance evidence. | Restrict Portainer access, remove exposed diagnostics, pin immutable images, disable unsafe configuration rendering, and keep encrypted secret escrow separate from both backup parts. A restore rehearsal must include controlled access to the matching application secret and pepper without recording them in the rehearsal evidence. |

Sequence the maintenance as: verified two-part backup and encrypted off-host copy; isolated recovery proof; final-Admin and MFA recovery plan; prepare database/application/pepper migration mechanics; quiesce writes; rotate one dependency at a time; restart exact verified services; run migration/readiness/authentication checks; revoke sessions if the incident decision requires it; monitor redacted failures; retain rollback material only for the approved recovery period. No part of this section authorizes the maintenance.

## Production security checklist

Before internet exposure:

1. Pin the exact qualified `sha-<commit>` image and verify its digest and embedded build SHA.
2. Set unique high-entropy application secret, credential pepper, PostgreSQL password and VAPID private key; keep them out of Git and backups intended for ordinary data export.
3. Require secure cookies, exact public hosts, exact HTTPS WebAuthn origin/RP ID, and only the reverse proxy's narrow CIDRs. Reject direct-origin access and bind any deliberately published origin port to loopback unless the deployment network design provides an equivalent boundary.
4. Enroll every affected Admin/Manager in TOTP before enabling required-MFA flags; run `python -m app.cli production-check` and require all security FAIL rows to be resolved.
5. Restrict database and application networks; PostgreSQL must have no public host port. Apply outbound firewall/egress policy for Web Push and external racing sources.
6. Terminate TLS at the trusted proxy, preserve one valid forwarding value, verify HSTS/Host/CSP/cookie headers, and test direct and malformed-forwarding requests.
7. Configure monitoring for login/MFA throttling, account/role/factor/reset/device audit events, scheduler health and repeated push/source failures without logging secret material.
8. Rehearse encrypted PostgreSQL plus `/app/data` backup/restore, verify least-privilege volume ownership, and protect backup access independently of the application.
9. GitHub's API reported `main` unprotected on 27 October 2026 and again on 6 November 2026. Before production promotion, configure branch protection to require the release gate, prevent force-pushes/deletion and unauthorized direct pushes, then directly verify it and retain immutable GHCR artifacts. Repository governance is a manual GitHub setting and was not changed by this audit.
10. Complete the staging acceptance matrix below before a separately authorized production promotion.

## Security staging acceptance

- Exercise ordinary, Manager and Admin PIN login; malicious `next` values; TOTP success/failure/replay/recovery; passkey register/login/remove; logout; current/other-device revocation; credential reset; status disable/reactivate; and final-role revocation.
- Prove regional Manager/Sub-Manager boundaries against pending and active Manager/Admin targets, plus Viewer, Contractor, cross-region and unassigned Workday/map access.
- Confirm required-MFA rollout using pre-enrolled accounts and the ordinary-access bootstrap sequence. Do not enable it first on an unenrolled privileged account.
- With staging-only VAPID credentials, test Chrome/Android and installed-iOS flows against real provider endpoints, then inspect that redirects, oversized responses and non-allowlisted subscriptions fail safely. Keep Push disabled if this test is not deliberate.
- Verify the reverse proxy, direct-origin denial, trusted forwarding, exact Host/origin, secure cookies, HSTS and outbound firewall rules from the real network path.
- Confirm old sessions, resets and challenges fail after privilege/status/credential changes; review redacted Audit and logs for every test.
- Confirm personal offline content is bounded and that reconnecting after logout/account switch clears the prior namespace.
