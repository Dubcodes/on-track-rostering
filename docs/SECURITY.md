# Security

## Authentication

Credentials use Argon2id with per-hash salts and an optional deployment pepper. Normal role PINs require 6–32 ASCII digits. Admin requires an 8+ digit PIN or a 12+ character password. A passkey cannot elevate an account whose persisted primary credential is below that Admin floor. Login errors are generic. A keyed email/IP throttle blocks after five failures in a 15-minute window.

The first Admin can only be created from `python -m app.cli create-admin`; no public route bootstraps authority. Public signup, when enabled, creates only a pending request with a requested region and no role, person link, or roster access.

Invitations use 40-byte URL-safe random tokens; only SHA-256 hashes are stored. They expire, are single-use, and a new invitation revokes unused invitations for that email. The browser posts the fragment token to a no-store metadata endpoint so email/name are authoritative without putting the secret in a query string or persistent storage. Activation locks the row, verifies credential confirmation server-side, and links an available Person without manufacturing or renaming a roster identity. A corrected account display name remains User-only. Successful activation mints the normal trusted-device session unless existing MFA policy requires its second factor.

Primary credential recovery is Admin-issued globally or may be issued by a scoped Manager for an ordinary Employee, Contractor, or Sub-manager account that the existing account-administration policy permits them to control. Pending and active Manager/Admin authority are both protected, so lower privilege cannot reset, relink, disable or otherwise control a future privileged security context. Reset issuance locks the target User and rechecks that policy inside the service; it therefore linearizes with privilege grants instead of relying on an earlier route check. Local recovery remains available through `python -m app.cli reset-credential --email ...`. Browser reset links are absolute URLs built from the configured trusted WebAuthn/application origin, never the request Host header, and carry the random token only in the URL fragment. Only its SHA-256 hash is stored; it expires after 60 minutes, and issuing a replacement revokes earlier unused resets. Completion locks the User and reset in the same order used by authority changes, applies the existing role-aware credential floor (including pending Admin grants), advances the auth epoch, revokes trusted devices and user-bound login challenges, and preserves identity, roles, Contractor state, passkeys, TOTP, and recovery codes. Staging, activating, revoking or changing protected authority revokes outstanding reset links and challenges. A reset never activates pending grants. Raw links and credentials are shown or accepted only at their bounded one-time surfaces and are excluded from audit detail.

Contractor invitations require an explicit Person link and fixed Contractor role/scope. The resulting account has no Crew View or management surface, and direct-route policy checks enforce the same boundary as navigation. Temporary access expiry is checked at login and trusted-device resolution; bounded refresh also marks the account expired, advances its auth epoch, revokes devices, and emits redacted audit events without deleting identity or roster history.

## Sessions and elevation

Trusted-device cookies contain opaque random tokens; only hashes are stored. Session cookies are HttpOnly, SameSite=Lax, and Secure when configured. CSRF cookies are SameSite=Strict and compared with a server-stored hash on every mutation. Origin and Sec-Fetch-Site are checked as defense in depth. Every authenticated account type may list and revoke only its own trusted devices; revoking the current device clears its cookies and signs it out.

Standard server trust defaults to a 90-day activity window and elevated roles to 14 days, capped by absolute 180-day and 30-day defaults respectively. The database expiry may advance on authenticated activity only inside that absolute cap; ordinary middleware responses do not reissue the browser cookie. The oldest devices over the configured limit are revoked. Route handlers exclusively own cookie issue, replacement and deletion, so logout, current-device revocation and credential replacement cannot be undone after the handler returns. Primary-authentication time is stored separately; sensitive factor, privilege, invitation, and account-lifecycle actions require it within the configurable 15-minute default. Role changes increment `User.auth_epoch`; an older Employee device with a stale epoch is rejected rather than silently becoming Admin.

Passkey rows store credential IDs, public keys, counters, and transports—never biometrics or private keys. Registration challenges are random, hashed at rest, five-minute, one-use, and bound to the authenticated account and trusted device. Authentication challenges are one-use. Challenge creation is rate-limited, expired rows are pruned, and authentication locks the credential through challenge consumption and counter verification. The maintained `webauthn` library verifies RP ID, configured origin, signature, user verification and counter. Registration requires a discoverable credential so username-less login works. Removing a passkey requires fresh authentication and cannot remove the final policy-relevant factor.

Optional TOTP secrets are encrypted with Fernet using domain-separated key material derived from the deployment `ONTRACK_SECRET_KEY`. Setup remains inactive until a valid code confirms it. Verification tolerates one 30-second step either side and updates the last accepted counter while holding the factor row lock, preventing replay across concurrent requests. User/address guessing and challenge issuance are independently throttled. Confirmation creates ten 64-bit recovery codes, displays their plaintext once, and stores only SHA-256 hashes. Codes are user-scoped and atomically single-use; regeneration invalidates unused predecessors, and factor disable removes the set. Recovery use and lifecycle changes are audited without raw code material. Enabling/disabling or regenerating a factor requires fresh authentication, advances the auth epoch, retains only the current trusted device, and creates redacted audit events. Admin/Manager enforcement flags default false to avoid locking out bootstrap accounts; readiness fails if a covered active or pending account lacks confirmed TOTP. Enforced roles cannot disable required TOTP. A verified passkey is a strong login path and does not also require TOTP.

New grants to existing accounts are `PENDING` and confer no authority. An account with no active grant is a preserved no-access record: it cannot mint or resolve a session, use passkey login, receive protected notifications, or regain published access merely through its Person link. A primary credential login activates eligible pending grants and mints a device with the correct shorter elevated lifetime. Managers may stage ordinary Employee, Casual, Contractor, or Sub-Manager grants only where both their Region authority and target-account administration scope allow; Admins may stage broader explicit grants, including Manager. When MFA is mandatory, an account must enroll TOTP under ordinary access before an Admin can stage Manager/Admin authority; direct privileged creation and Manager invitation fail closed. Active-grant revocation invalidates every target session. The final active Admin grant/account cannot be revoked or disabled through the UI, and concurrent final-Admin revocations serialize through a PostgreSQL transaction-scoped global lock and fresh active-grant lock. An Admin cannot disable their own current session.

## Authorization and data visibility

`app/auth/policy.py` is the central backend authority. Operational roster routes check Admin or regional Manager/Sub-Manager authority; account and regional catalogue administration requires Admin or regional Manager. Published Day/JSON reads check regional Crew View or direct assignment. Employee reads never follow the draft pointer. Regional account queries include only linked people or grants in the Manager's regions. Viewer may read the published regional roster but never receives management detail, Team Hours, leave administration, assignment accommodation addresses, or another Person's private assignment note. Private assignment detail is filtered when the read model is built and is available only to the assigned Person and scoped Manager/Sub-Manager authority.

Crew-management mutations validate the target person's home region against the actor's management scope. Open applications require a linked Employee role in the workday region plus effective base-position eligibility; Contractors and Viewers cannot apply. Applicant selection requires regional management authority and rejects applications from an older publication. Decline lookup binds the authenticated person's ID, current published revision, and stable slot key, preventing another user's assignment from being declined by ID substitution.

Person work email is normalized and validated through one identity service before create, edit, link, invite, signup approval, batch metadata apply, or neutral import. Active-Person uniqueness is global and case-insensitive. A linked Person and User must retain the same normalized email; an unlinked User with the same email remains available for explicit reconciliation and is never claimed or merged automatically. PostgreSQL advisory transaction locks serialize competing writes even when no matching Person row exists. Legacy duplicate/mismatch records are reported to authorized administrators without mutation; a database unique constraint is deliberately deferred until those records have been reconciled.

## Browser and output protection

Jinja autoescaping remains enabled. User text is rendered as text, never as a template. SQLAlchemy parameters all database values. Responses set nonce-based CSP without broad `unsafe-inline`, frame-ancestor denial, no-sniff, same-origin referrer, restrictive browser permissions, and HSTS when secure-cookie production mode is enabled. Validated six-digit track colours are emitted only in nonce-bearing style blocks/data attributes. Authentication return targets pass one server policy: local absolute paths only, with schemes, authority, fragments, controls, backslashes, protocol-relative forms and encoded separator tricks rejected. Outbound racing/map HTTP validates the initial URL and every redirect before contact. Only HTTPS on the official Love Racing/HRNZ host boundary and standard port is permitted, redirects stop after three hops, optional provider/path validators remain in force, and only the small source `Accept`, `User-Agent`, and request content-type header set may cross a redirect. Private, malformed, credential-bearing, fragmented, control-character, and untrusted destinations fail closed. CSV intended for spreadsheet use neutralizes formula-triggering cells; exact Admin-export values remain separately available under `machine-readable/`.

Forwarded client/origin authority is accepted only when the immediate peer is in the configured trusted-proxy CIDRs and each forwarding value is singular and valid. Direct clients and malformed forwarding fall back to the socket peer and internal request origin. Login/signup throttling and same-origin checks consume this shared resolution.

Audit detail is recursively redacted for credential/token/cookie/secret keys. The application must never log raw invitation or credential-reset URLs beyond their one-time Admin display.

## Push and residual risks

Push subscription endpoints and key material are encrypted at rest with separate domain-separated Fernet key material. The VAPID private key is environment-only. Subscription registration and every delivery revalidate HTTPS/default-port endpoints against the configured browser-push provider allowlist and require all resolved addresses to be public. Redirects are disabled, transport time is bounded, decoded responses are capped at 64 KiB, and subscription/key payload sizes are limited. Delivery stores bounded retry/permanent failure state and never logs endpoint or key material. DNS rebinding cannot be eliminated solely by pre-resolution, so production egress must also deny internal, link-local, loopback and metadata destinations. Already-cached offline content cannot be remotely erased while a device never reconnects; caches are therefore narrowly scoped to roster reads and are deleted on the next observed account switch/logout.

The Admin readiness panel and `python -m app.cli production-check` identify unsafe production defaults, database/scheduler health, optional Web Push state, build identity, and MFA-policy warnings without exposing configured values. They support deployment review but do not replace real HTTPS WebAuthn qualification, trusted-proxy review, verified backup restoration, monitoring, or targeted penetration testing.
