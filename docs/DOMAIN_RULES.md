# Domain rules

- On Track stores authoritative workdays directly. External calendar/programme records are planning assistance.
- Same-provider observations with the same stable meeting identity may correct programme facts. A partial or awaiting schedule never downgrades a complete programme. Date or Track identity changes remain conflicts for review.
- Source facts may update only an unpublished linked draft automatically. Published revisions are immutable; applying the latest programme creates or updates a private draft and still requires Preview → Publish.
- Automatic Track maps come only from trusted Love Racing hosts and validated JPEG/PNG/WebP content. A Manager's manual image for their Region takes precedence until explicitly reset; a failed refresh retains the last good automatic image. Track-map refresh is independent of a racing-provider toggle.
- A source Track identity maps to one existing canonical Track UUID and inherits that Track's Region. Online Sources never owns a second map Region or map reference, never silently confirms a fuzzy suggestion, and never creates another Track when the canonical Track already exists.
- The racing scheduler is database-singleton work. Provider discovery runs on a bounded 48-hour cadence, while detail cadence tightens as race day approaches and backs off after failures. Disabling a racing provider stops that provider's automatic racing-data requests, including programme detail; source failure never blocks manual Workday creation or editing.
- `On Track Rostering` is the internal project name. User-facing product identity comes only from global Admin-configurable branding; changing it does not change authorization, roster data, or internal/database identity.
- Workday categories have stable codes: Race Day, Trials, Travel Day, Rig Day, Office Day, Training Day, Other.
- Publication follows Draft → Preview → Publish. Drafts are invisible to crew; authorized Managers can rediscover draft-only days and unpublished changes from Month/List without replacing the published crew view.
- A Workday has one shared Manager draft. Draft mutations and Publish carry an optimistic Workday version, lock the Workday row, and reject stale submissions instead of overwriting newer work.
- An account is not a rosterable person. Linking must not create duplicate crew identities.
- A linked Person and historical/published assignment never grant application authority by themselves. A User must hold at least one active RoleGrant to authenticate or use a protected session. A User with only revoked grants is preserved as a no-access record.
- Home region is a default, not a prison. Event assignment can grant one-off cross-region visibility. A person's own cross-region marker compares the Workday region with `Person.home_region_id`, never with role scope; an unknown home region is neutral.
- Roles combine authority and independent region scope. Viewer is broad read-only, not quasi-Manager. Sub-Manager can perform practical regional rostering but not system security administration.
- Pending role grants authorize nothing, but pending Manager/Admin authority is protected from lower-privilege account control exactly like active Manager/Admin authority. Existing-account grants activate only after the account owner next proves their primary credential. Previously issued reset links and user-bound challenges are revoked across authority transitions. Managers may grant only regional Sub-Manager authority in a region they manage.
- When Admin or Manager MFA is mandatory, confirmed TOTP must exist before that privileged grant is staged. The supported bootstrap is ordinary linked access, factor enrollment, then pending privileged grant and primary-login activation; direct privileged creation and Manager invitation fail closed instead of bypassing enrollment.
- Crew groups are editable many-to-many browsing/suggestion data, never authorization barriers.
- Capability attaches to a base position such as CCU or VT. `CCU 1`/`CCU 2` are event slots of CCU unless deliberately modelled otherwise.
- Regional Position presets are simple ordered sets of active Base Positions for Thoroughbred, Harness, or Trials. They never contain people, travel, or notes. Managers edit only their Regions, Admin may edit globally, and removing an override restores the built-in fallback.
- Effective position recommendation precedence is: Manager block; Employee opt-out; explicit Manager/Employee allow; qualified worked history; otherwise not proactively eligible. Managers may still manually assign with a warning.
- Published assigned slots record raw `WORKED` history; drafts never count. Automatically sourced history becomes qualified inferred eligibility only after at least two distinct current-published scheduled Workdays for the same canonical Base Position. Multiple slots on one Workday count once and canonical aliases count together. Trusted legacy/imported `WORKED` history remains preserved and eligible even when it has no source revision.
- ASSIGNED, OPEN, TBC, and MANAGER_ACTION_REQUIRED are distinct assignment states.
- Open-position applications attach to a specific published revision and stable slot key. Managers select an applicant into a draft; only Publish makes the assignment authoritative. Duplicate and stale applications are rejected.
- Employee decline is an exceptional direct authoritative action. It creates a new immutable published revision atomically: `OPEN_IMMEDIATELY` produces OPEN, while `MANAGER_REVIEW` produces MANAGER_ACTION_REQUIRED. It never mutates an older publication.
- Track colours are data and may repeat across regions. Names/text always accompany colour.
- Normal day notes are visible to rostered Contractors, scoped Crew View, operational management, scoped Viewers, and Admin.
- Event-only Contractors may see the published coworkers' names, Positions and relevant start/finish times only on a Workday to which they are assigned. They never gain the regional Crew calendar or another Person's note, transport, accommodation, contact details, Hours, draft or management data. The same reduced projection is used by HTML and user-namespaced Day JSON.
- Viewer is a Region-scoped published-roster reader, not management oversight. Viewer cannot read Team Hours, leave administration, another Person's private assignment note, or assignment accommodation address. Private assignment detail is visible only to the assigned Person and scoped Manager/Sub-Manager authority.
- A Person may hold multiple Positions on one Workday, including through Open Position selection. The Builder warns immediately and requires the Manager to choose Move, Keep both, or Cancel. Move clears only the former row's Person so the Position remains Unassigned; Keep both is deliberate. Position-specific start/end times may differ; Person/day participation combines all of that Person's assignment spans into one earliest-start/latest-finish span, so Hours, reminders, and generated Travel never double-count multiple Positions. Travel is one authoritative person-level plan shared by all of the Person's Position rows. A linked generated Travel Day remains a separate Workday. No automatic half-hour or meal-break deduction occurs.
- Person unavailability is an inclusive whole-date operational range, not payroll, entitlement, or an approval workflow. It is advisory: a Manager may deliberately roster a Person on leave, and creating leave never rewrites or removes an existing roster. Dates are visible in authorized rostering workflows; the optional management note remains restricted to authorized Admin/Manager leave administration.
- Race Day timing is derived by default. First race rounds down to the previous quarter-hour, then the Region Race Day setup lead is subtracted to calculate On track. The Workday revision's Track-travel snapshot is subtracted from On track to calculate the default Start. Last race is the scheduled **start** of the final race: Race clear is `ceil_to_quarter(last race start + 10 minutes)`, and Finish adds Pack-up and optional Return travel. The 10-minute allowance is a stable code-level domain policy, not an environment, Admin, SystemSettings, or Workday setting. The old Re-Deputy +3-minute rule is superseded.
- Managers may explicitly override Race Day Start, On track, and Finish and may reset each value to its calculation. Assignment Start remains the highest-priority Person call-time override; standard overnight hotel-to-Track timing remains next, SELF_TRAVEL and NOT_REQUIRED use On track, and vehicle/custom/unassigned transport uses Workday Start.
- Published historical revisions use their own Track-travel snapshot and never read a live Track default. Changing Track master data cannot alter published timing, Hours, reminders, or Crew views.
- Allowances and public holidays are informational and never payroll calculations.
- Operations group related days and explicit TravelLegs. An enabled standard overnight plan generates a parent-owned previous-day Travel Day and publishes it atomically with its Race/Trials Day. Disabling travel cancels rather than deletes that linked day; re-enabling reuses it. Assignment travel values are nullable person overrides resolved against immutable revision defaults, never copied defaults.
- Workdays are scheduled, cancelled, or abandoned. Cancelled/abandoned history remains visible but is excluded from worked Hours, ordinary reminders, Open Positions, and active conflict blocking; an authorized Manager may reinstate it.
- Personal Month shows the linked Person's own authoritative published assignments, including actual cross-Region work, plus eligible published Open Positions. Future source-calendar cards come only from the Person's Primary Region and only after that Region's latest current published SCHEDULED Workday; with no such horizon they start today. Draft, cancelled and abandoned Workdays do not move the horizon. Management roles never turn Personal Month into a crew calendar; Crew view is the authorized regional all-crew published calendar. Contractors and unlinked accounts gain no regional planning feed.
- A published Workday is rescheduled by abandoning it and creating a linked replacement, never by mutating its date. The replacement clones the source's current published roster into a fresh immutable publication, supports A → B → C chains, and receives freshly generated Travel. It does not inherit external-event identity, applications, personal responses, Operation or generated-Travel identity, or programme/source provenance. A predecessor with a replacement cannot be reinstated.
- Assigned Employees and Contractors respond to a replacement per Workday and Person. ACCEPTED and DECLINED are explicit; no response is Pending. A decline signals Manager action and never automatically removes the assignment.
- Employee notes, personal timing, and Making own way are private stable Workday+Person records. They survive publication revisions; personal timing affects only that employee's Hours, while management Hours remain the published roster span.
- Master records are archived instead of casually deleted once historically referenced.
- Notification generation is an idempotent event-outbox concern. Roster-change audience includes both removed and newly assigned users. Reminder keys bind publication, person, and reminder kind. Push delivery failure must never roll back roster publication or employee decline.
- Employee and Manager capability preferences are independent decision families. Clearing either family never removes the other family or published `WORKED` history.
- Fortnight totals use only the current published revision and the assigned person's authoritative start/end span. Allowance entitlements never increase that worked total.
- Team Hours treats every weekday alike. A Person with active leave appears even without work; worked-on-leave cells show both states. Mobile hides visible daily durations while retaining duration/location in the cell title and accessible label.
- New Race Days default to a 15-minute early truck offset. `Vehicle.is_truck` changes only the effective Person start; explicit assignment timing, overnight hotel timing, and self/no-transport priority remain authoritative, and the Workday Start is unchanged. Historical revisions migrated with zero offset.
- A Vehicle owns one home Region, and Manager mutation authority follows that owning Region. An authorized roster Builder may assign another Region's active Vehicle as a borrowed Vehicle; borrowing does not transfer ownership.
- Track physical address, Region operational base, and accommodation address are operational place data. Published revisions snapshot Track/base addresses; travel minutes remain configured values and are never route-derived. Cambridge Harness and Cambridge Synthetic are distinct Tracks.
- Same-date Race and Trial source rows remain independent. Calendar presentation may associate them only for the same Track and discipline when both first times are known and no more than 180 minutes apart. A published Workday remains authoritative; related Trial context never silently changes Race Day Start, On track, Race clear, or Finish.
- Pasted operational leave uses exact active-Person name matching and explicit DD/MM/YYYY or YYYY-MM-DD dates. Preview writes nothing; Apply is atomic and exact active ranges are idempotent.
- Person UUID is roster identity, User UUID is account identity, and normalized email is the human/login identifier. Deputy employee IDs are not ongoing identity. Metadata worksheet apply changes Person metadata only; setup links are generated separately, shown once, and never emailed automatically.
- An active Person's normalized work email is globally case-insensitive unique across Regions. A linked Person/User pair must use the same normalized email. A matching unlinked User is an explicit reconciliation case, not an error that authorizes automatic linking or merging. Legacy conflicts remain visible for deliberate repair; they are never silently converged.
- Personal fortnight totals depend on a User–Person link, not on holding an Employee role, and never infer or deduct unpaid breaks.
- Fortnight boundaries come from the persisted system setting, defaulting to `2026-08-31`; both personal and Team Hours use the same anchor. Team Hours retains detailed rows and presents a compact fourteen-day per-Person matrix with Search, Crew-group and Region filters, Track colour and leave state; it has no weekend-specific treatment and hides visible duration labels on mobile while preserving accessible detail.
- TOTP recovery codes recover only the optional TOTP factor: ten are shown once, stored as SHA-256 hashes, consumed atomically once, replaced wholesale on regeneration, and removed when TOTP is disabled. Primary-credential reset is a separate fresh-auth Admin, scoped-Manager-for-ordinary-accounts, or local CLI workflow with its own hash-only 60-minute single-use token and session/challenge invalidation.
- Regional Managers may link in-scope existing accounts and People and create one-time Employee, Casual, Contractor, or Sub-Manager invitations. Admin may create a Manager invitation for an in-scope Person. Person-level regional grants in Crew remain bounded by the unchanged role-grant and account-administration policy. Those actions do not merge account identity with roster identity or grant out-of-scope authority.
- Contractor invitations always bind the new User to the intended in-scope Person. Contractor access expires after the later of authoritative future participation or manual extension plus the configured inactivity period (default 30 days); recalculation can extend but never shorten an existing later expiry. Expiry is non-destructive and authorized management may reactivate access.
- Person and User remain distinct identities. Crew presents one Person-centric management surface, but displays both UUIDs and applies account controls only through server-side scope policy. Managers may control ordinary Employee, Contractor and Sub-manager accounts in administered Regions after fresh authentication; active Manager/Admin accounts require Admin authority. Setup/reset links are one-time, hash-only-at-rest and never emailed automatically.
- Active Base Position identity is global and canonical; CrewGroup is classification metadata. Aliases and numbered event labels resolve through the shared canonical identity, while existing ambiguous legacy rows remain visible for explicit convergence rather than guessed mutation.
- Operational-notice publishing defaults to active Manager/Sub-manager Region grants. An Admin override is an explicit record and may intentionally contain no Regions. One notice may target several Regions relationally; audience unioning prevents duplicate push delivery. Personal error reports retain only safe description/User/Person/build/path/timestamp context and New/Reviewed state.
- The one-time Deputy capture importer is an isolated transition boundary: manually supplied text only, allowlisted published schedule fields only, People but never Users, existing publications win, unresolved locations skip safely, and the apply transaction emits no roster notifications.
- The upcoming-work feed returns today only when the person is rostered today, followed by at most the next three actual published workdays across month boundaries; the client prefetches those server-selected days sequentially.
- Normal user-facing pages use operational language and do not expose development notes, migration/convergence instructions, raw debug diagnostics, internal implementation terminology, or a global build SHA/version footer. Technical identity and diagnostics belong only on intentional Administration, Audit, Data Import, or diagnostic surfaces.
- Deferred: configurable Open Position auto-accept requires a separate policy workflow; current applications remain Manager-approved.
- Onboarding metadata batch writes contain only explicitly edited exact Person UUID rows. Blank email and Primary Region are valid Person metadata; setup invitation remains a separate action requiring both.
- Dice requires a positive active linked working account, matching Primary Region, Crew Group membership and canonical Position eligibility. Casual, Contractor, disabled, expired and unlinked People are excluded from Dice but remain available for authorized manual selection.
- Vehicle capacity is total distinct People including the driver. Capacity prompts evaluate the proposed final association: replacing an occupant does not prompt when the replaced Person has no other Position in that Vehicle, while a true additional Person still requires Kick last, Keep, or Cancel. Cancel preserves the former selection; duplicate Position rows do not multiply occupancy or drivers. A deliberate over-capacity plan remains visible at Preview. Every used truck has exactly one deliberately designated driver with explicit Person truck-driving qualification.
- A successful automatic Track map is due for refresh every 90 days; a failed attempt becomes due after one day so a transient source failure cannot defer recovery for a quarter. Manual override wins until reversion, and failure never removes the last fully validated local image. Upload/refresh performs complete URL, handler-path, redirect and content validation; ordinary catalogue/Day checks reject missing, signature-invalid, dimension-mismatched, or size-mismatched files from bounded metadata/header reads and stream available files instead of loading them fully into application memory.
- Source vehicle-like identifiers such as `684`, `685` and `Rav91` are transition conflicts, never Base Position identities.
